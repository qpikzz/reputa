- [x] **COMP-002** — Компонент диаграммы "Благонадёжность" (ScoreGauge, frontend)

  Переиспользуемый спидометр «Благонадёжность (0–100)», один пропс — числовое значение 0–100. Позиция красного маркера, длина синей заливки и цвет числа/точки вычисляются внутри компонента из значения. Структура сверху вниз:

  1. Заголовок «Благонадёжность (0–100)» — мелкий текст по центру над диаграммой (i18n-ключ `scoreGauge.title`).
  2. Полукруглая шкала (дуга на 180°):
     - тонкая цветная подложка вдоль всей дуги, разделённая на 3 зоны: розовая/красная слева (низкие), жёлтая/оранжевая посередине (средние), зелёная справа (высокие);
     - поверх подложки — толстая синяя дуга-заливка, показывающая прогресс от начала шкалы до текущего значения (при значении 100 заливка покрывает всю дугу);
     - риски и подписи делений шкалы в точках 0 (крайняя левая), 20, 40, 60, 80, 100 (крайняя правая);
     - красная вертикальная риска-маркер на дуге — точная позиция текущего значения (отдельный элемент, не край синей заливки).
  3. Крупное числовое значение по центру под дугой, цвет по диапазону: низкая 0–39 / средняя 40–69 / высокая 70–100 (симметрично цветовым зонам подложки).
  4. Маленькая точка-индикатор под числом, цвет совпадает с цветом числа.

  Технически: чистый SVG, без сторонних графических библиотек и новых зависимостей. `value = null` — состояние «оценки нет» (без заливки, маркера и точки, вместо числа «—»), необходимо карточке APP-005 до расчёта оценки.

- [x] **AUTH-008** — Иллюстрация рядом с формой на страницах входа/регистрации/входа для персонала

  На `/login/`, `/registration/`, `/loginWork/` рядом с карточкой формы (справа) добавляется фото — по одному на страницу, файлы уже лежат в `public/img/` (найди в проекте актуальные имена файлов, не изобретай их). Отступ между карточкой формы и фото — 4rem. Скругление углов фото — то же значение, что и у карточки формы. Высота фото равна высоте карточки формы и подстраивается под неё динамически (карточка меняет высоту при появлении подсказок/ошибок валидации — фото должно следовать за этим изменением). ## Этап 3. Заявка и скоринг по выписке

- [x] **APP-001** — Форма новой заявки (frontend `/user/new`)

  Поля: сумма (валидация: от 1 000 до 10 000 000, ошибка "Укажите сумму больше нуля" при пустом/некорректном значении), цель/причина кредита (свободный текст, textarea), телеграм (@username), актуальный телеграм-канал (@channel — обязательное поле, без него форма не отправляется), выписка из банка (загрузка файла), чекбокс согласия с политикой конфиденциальности. В одной строке с кнопкой "Запросить" — поле пароля (доп. верификация личности перед отправкой заявки). Кнопка "Запросить".

  Плейсхолдер поля "Причина" — один из 7 заранее заданных вариантов цели кредита, выбирается случайно при каждой загрузке страницы:
  - На корм для уток
  - На путешествие в Дубай
  - На курс по успешному успеху
  - На новую версию себя
  - На курсы актёрского мастерства
  - На абонемент в спортзал
  - На книгу по саморазвитию

- [x] **APP-002** — Эндпоинт создания заявки (backend)

  Приём данных формы и файла выписки, создание записи Application со статусом "в обработке". `UserNew.jsx` подключён к `POST /api/applications` (multipart/form-data).

- [x] **STMT-001** — Парсинг банковской выписки

  При загрузке файл сразу парсится в структурированные данные (остаток, поступления, траты по категориям за 3 месяца). Сам файл не сохраняется — хранятся только структурированные данные. Реализовано в `app/scoring/stmt_parser.py` (Альфа-Банк, СберБанк, Озон Банк), подключено в `POST /applications` как валидация загружаемой выписки; фикстуры и тесты — `tests/test_statement_parser.py`, `tests/fixtures/`.

- [ ] **STMT-002** — Расчёт скоринга по выписке

  Расчёт вклада в итоговую оценку на основе среднего остатка, регулярности поступлений, доли трат на необходимые товары. Формирует часть позитивных сигналов / факторов риска в ScoreResult.

- [x] **APP-003** — Пороговая автообработка заявки

  После расчёта итоговой оценки сравнение с порогами из настроек сотрудника (EMP-002): если оценка ≤ порога авто-отклонения — статус "авто-отказано"; если оценка ≥ порога авто-одобрения — статус "авто-одобрено"; иначе заявка уходит в очередь сотрудника.

- [x] **APP-008** — Автообработка перебором случайных сотрудников (уточнение APP-003)

  Уточнение логики автообработки: пороги автообработки становятся персональными для каждого сотрудника (сейчас это один общий синглтон `threshold_settings` с id=1, см. EMP-002). При подаче заявки после расчёта итоговой оценки бэкенд берёт случайного сотрудника и проверяет, подпадает ли рейтинг заёмщика под его пороги (score ≤ порога авто-отклонения или score ≥ порога авто-одобрения):
  - подпадает — заявка закрывается автоматически, и именно этот сотрудник впоследствии указывается как сотрудник, закрывший сделку;
  - не подпадает — берётся следующий случайный сотрудник из оставшихся, и так до конца перебора;
  - не подошёл ни один — заявка остаётся в очереди сотрудника (`in_queue`), как сейчас (в EMP-003/EMP-004 такие заявки видит любой сотрудник).

  Изменения: (1) хранение порогов переносится с синглтона на связь «сотрудник → собственные пороги» (миграция существующей строки БД; фронтенд EMP-002 уже работает через `/api/employee/settings` — API сохраняется); (2) при автообработке заполняется `Application.decided_by` — ссылка на сотрудника, закрывшего сделку (колонка введена в EMP-005, при ручном решении сотрудника она уже заполняется в EMP-006).

- [x] **APP-009** — Автоматический запуск скоринга при создании заявки

  При создании новой заявки (APP-002) автоматически запускать полный пайплайн анализа и присвоения итоговой оценки (STMT-002 по выписке + TG-002/TG-003 по телеграму, если данные есть) сразу после сохранения заявки, без отдельного ручного триггера. Результат сохраняется в ScoreResult и сразу используется пороговой автообработкой (APP-003).

- [x] **APP-004** — Список заявок пользователя (frontend `/user/my`)

  Таблица заявок пользователя: id, статус, сумма, дата создания заявки, итоговая оценка. Сортировка по дате создания (по умолчанию — сначала новые). Данные — `GET /user/applications` (backend, APP-007); `UserMy.jsx` на реальных данных, моки убраны.

- [x] **EMP-002** — Настройка порогов автоматизации

  Часть `/employee/settings`, блок "Автоматизация": порог "авто-отклонение ≤ X" и порог "авто-одобрение ≥ Y". Backend хранит оба порога в БД (не хардкод), их использует APP-003.

- [x] **EMP-003** — Список актуальных заявок (frontend `/employee/newApplication`)

  Таблица заявок, ожидающих решения сотрудника (не попавших под автообработку): id, статус, ФИО заёмщика, сумма, итоговая оценка. Frontend готов по образцу APP-004 + поиск по ФИО (см. `openspec/tasks/EMP-003.md`); **страница показывает только `in_queue`** — решённые заявки из очереди исключаются; данные — заглушка до backend-эндпоинта очереди сотрудника. Мock-заявки вынесены в общий `frontend/src/mocks/employeeApplications.js` (8 записей с полным профилем, историей скачиваний и данными решения) и используются обеими страницами сотрудника + карточкой EMP-005.

- [x] **EMP-004** — Список всех заявок (frontend `/employee/application`)

  Таблица всех заявок вне зависимости от статуса: id, статус, ФИО, сумма, итоговая оценка. Frontend готов по образцу APP-004 + поиск по ФИО и ID заявки; данные — реальные через `GET /api/employee/applications` (см. `openspec/tasks/EMP-004.md`), при недоступности API — заглушка.

- [x] **EMP-005** — Детальная карточка заявки сотрудника (frontend, переиспользуемый компонент)

  Единая карточка заявки, открывается по `?menu={id}` на обеих страницах: `/employee/application` и `/employee/newApplication` (общий компонент `ApplicationDetail`). То же, что видит заёмщик в APP-005 (id, ФИО, сумма, цель, спидометр), ПЛЮС полный разбор, недоступный заёмщику: блок "Рекомендации системы" (позитивные сигналы и факторы риска — бейджи с галочками/предупреждениями в две колонки), блок "Психологический портрет заёмщика" (три метрики по шкале 0–10) и блок "Отчёт для кредитного комитета" (кнопка скачивания + история скачиваний) — бок о бок двумя колонками выше "Итоговой оценки", кнопки "Одобрить"/"Отклонить" (EMP-006). После решения карточка показывает ФИО и логин сотрудника, принявшего решение: `Application.decided_by` (FK users) + `decided_by_employee` в `GET /employee/applications/{id}`. См. `openspec/tasks/EMP-005.md`.

  > Поле `decided_by` вводит внутризадачный минимум связи «заявка → сотрудник»; полный перенос порогов на сотрудника и автообработку — APP-008 (там же `decided_by` будет заполняться при автообработке).

- [x] **EMP-006** — Эндпоинт решения по заявке (backend)

  Приём решения сотрудника (одобрить/отклонить), обновление статуса заявки — изменение сразу отражается в `/user/my` у заёмщика.

## Этап 5. Telegram-скоринг

- [x] **TG-001** — Парсинг публичного Telegram-канала

  Получение сообщений канала через Telegram Bot API по адресу, указанному в заявке.

  > Реализация (см. `openspec/tasks/TG-001.md`): сообщения читаются через публичную web-preview `https://t.me/s/<username>` (Bot API не отдаёт историю каналов без членства бота). Модуль `backend/app/scoring/telegram_channel.py` — извлечение username, разбор HTML в список сообщений (текст + дата), `None` при недоступности канала.
  > Если канал недоступен или закрыт — просто не учитывается в оценке, без отдельной обработки ошибки для пользователя.

- [x] **TG-002** — Расчёт скоринга и психологического портрета по данным канала

  На старте — захардкоженный сценарий (заранее заданные позитивные сигналы, факторы риска, метрики портрета и текст отчёта для демо). Если будет время — реальный анализ лексики, частоты упоминаний работы, подписок на финансовые каналы (LLM+NER).

  > Реализация (см. `openspec/tasks/TG-002.md`): модуль `backend/app/scoring/telegram_scoring.py` — эвристики по лексике (работа/финансы/позитив → позитивные сигналы; долги/азарт → факторы риска), плотность упоминаний, регулярность постов по датам сообщений. Возвращает отдельный `TelegramScoringResult` (`score_contribution` 0–100, сигналы, метрики портрета 0–10, отчёт). TG-003 объединит его с оценкой по выписке.
  > **OCR фото** (дополнительно к TG-002): `backend/app/scoring/telegram_vision.py` — фото из постов (`photo_urls`, извлекаются парсером `telegram_channel.py`) скачиваются и распознаются через **Gemini 3.6 Flash** (ключ `GEMINI_API_KEY`, см. `.env`); распознанный текст (переводы, чеки, скрины банка) добавляется к корпусу поста перед анализом лексики. Без ключа или при ошибке сети/Gemini обогащение молча отключается — анализ работает по тексту.
  > **LLM-анализ GigaChat** (дополнительно к TG-002): `backend/app/scoring/telegram_llm.py` — семантический анализ корпуса + NER переводов (направление income/expense/transfer) через **GigaChat API Сбера** (Authorization Key `GIGACHAT_CREDENTIALS`, поток GigaChat-2). Скоринг-формула единая (`_score_from_evidence`); при недоступности GigaChat (нет ключа, ошибка, невалидный JSON) — откат на словарные эвристики `score_telegram()`. См. `openspec/tasks/TG-002.md`.

- [ ] **TG-003** — Интеграция telegram-сигнала в итоговую оценку

  Объединение сигнала из TG-002 с оценкой по выписке (STMT-002) в единый итоговый балл. Должно работать и в отсутствие telegram-сигнала (см. TG-001) — тогда используется только оценка по выписке.
